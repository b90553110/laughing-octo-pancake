Flyway conflicts across a team

Two branches, two migrations, one version number. Git merges them without complaint; Flyway does not.

~20 minutes · Flyway 12.4.0 · Spring Boot 4.1.1
Error strings quoted verbatim from flyway-core-12.4.0.jar. I did not execute this code.

Lesson 02 covered a single engineer applying migrations in sequence. Add a second engineer and a new class of failure appears, because Git and Flyway disagree about what a conflict is.

Git detects conflicts within a file. Two branches that each add a different file merge cleanly, even when those files carry the same Flyway version. Flyway then rejects the result. The failure therefore never appears in the pull request; it appears on the branch that merged second, after both reviews passed.

01Failure one: duplicate versions

Two engineers branch from main at version 6. Each adds V7__. Both pull requests pass review and merge. The next startup fails:

Found more than one migration with version 7
Offenders:
-> .../db/migration/V7__add_orders_status.sql (SQL)
-> .../db/migration/V7__add_users_phone.sql (SQL)

Flyway refuses to guess an order. It applied nothing and corrupted nothing; the build simply stops until an engineer assigns the versions.

Resolve it
  1. Identify which migration already ran anywhere outside a local machine. Renumber the other one.
  2. Rename the unapplied file to the next free version: V7__add_users_phone.sql → V8__add_users_phone.sql.
  3. Drop and recreate your local database, then start the application. Confirm Flyway applies the full sequence from empty.

Never renumber a migration that has already run on a shared environment. Renaming the file changes neither the checksum nor the recorded version, so Flyway will report a migration it applied but can no longer resolve.

02Failure two: out-of-order arrivals

This case is quieter and more dangerous. Engineer A merges V8__ on Monday, and every developer database and staging applies it. Engineer B, still on a branch cut last week, merges V7__ on Tuesday. Databases now hold version 8 but not version 7:

Validate failed: Migrations have failed validation
Detected resolved migration not applied to database: 7

Flyway refuses to apply version 7 after version 8 because spring.flyway.out-of-order defaults to false. That default is correct, and here is the precise reason: if Flyway applied version 7 late on some databases and in sequence on others, the two databases ran the same migrations in different orders. Any migration whose result depends on preceding state — a backfill, a constraint added to data another migration wrote — then produces different results per environment.

Recommendation

Leave out-of-order at false in every environment. Renumber the late migration to the next free version instead, which restores a single global order. Enable out-of-order only on a disposable local database, and only to avoid rebuilding it during exploratory work.

03Eliminate the collision instead

Both failures share one cause: sequential integers force every branch to guess the same next number. Three naming schemes exist. Choose by team size.

  • Sequential integers (V7__) — readable, and adequate for one or two engineers who merge frequently. Collides constantly beyond that.
  • UTC timestamps (V20260915103000__) — collisions require two engineers to create a migration in the same second. Ordering follows creation time rather than merge time, which remains correct because migrations that touch unrelated tables commute.
  • Timestamp plus ticket (V20260915103000__PROJ_412_add_phone.sql) — adds traceability from schema change to the work that required it.
V20260915103000__add_users_phone.sql
V20260915141500__add_orders_status.sql
 └── UTC timestamp: year month day hour minute second
Recommendation

Adopt UTC timestamps on any team of three or more. The cost is unreadable version numbers. The benefit is that the duplicate-version failure becomes impossible, which removes an entire category of broken builds on main. Decide once and enforce it in CI; a repository that mixes both schemes gets the drawbacks of each.

04Enforce the rules in CI

Every rule in this lesson and in Lesson 02 is mechanically checkable. Check them in CI, because review will not catch a version collision — each pull request is individually correct.

Check 1: migrations apply to an empty database

Run the full sequence against a clean database on every pull request. This single check proves more than the other two combined, because it executes the SQL rather than inspecting filenames.

CI job, abbreviated
# Apply every migration to an empty database.
# This is the only check that proves the sequence works.
services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_PASSWORD: ci
steps:
  - run: ./mvnw flyway:migrate -Dflyway.url=jdbc:postgresql://postgres:5432/ci

Check 2: no duplicate versions

ci/check-duplicate-versions.sh
#!/usr/bin/env bash
# Fail when two migrations share a version.
set -euo pipefail

dupes=$(ls src/main/resources/db/migration/V*__*.sql \
        | sed -E 's|.*/V([0-9.]+)__.*|\1|' \
        | sort | uniq -d)

if [ -n "$dupes" ]; then
  echo "Duplicate migration versions: $dupes" >&2
  exit 1
fi

Check 3: no modification of existing migrations

This check enforces the rule from Lesson 02 §06 mechanically, which matters because the cost of violating it lands on whoever deploys next rather than on the author.

ci/check-migrations-immutable.sh
#!/usr/bin/env bash
# Fail when a PR modifies or deletes an existing migration.
set -euo pipefail

changed=$(git diff --name-status "origin/main...HEAD" \
          -- src/main/resources/db/migration \
          | grep -E '^[MDR]' || true)

if [ -n "$changed" ]; then
  echo "Existing migrations modified or deleted:" >&2
  echo "$changed" >&2
  exit 1
fi
One exception to check 3

A migration added and modified within the same unmerged pull request has run nowhere shared, so editing it is correct. Compare against the merge base, as the script above does, rather than against the previous commit.

05Practices for a team

  • One migration per pull request wherever possible. Two migrations in one branch raise the odds of a collision and complicate renumbering.
  • Create the migration late. A migration written on day one of a two-week branch has two weeks to collide. Write the schema change when the code needs it.
  • Rebuild your local database after merging main. A local database that applied your branch's migration before main's produces a local ordering that exists nowhere else.
  • Deploy migrations ahead of the code that requires them, in a separate release. The schema then already supports the new code when it deploys, and a rollback of the code needs no rollback of the schema.
  • Never resolve a Flyway conflict with repair. Repair addresses checksum disagreement, not ordering or duplication. Reaching for it here hides the problem.
  • Grant production migration rights to the deploy pipeline, not to engineers. Manual application on a shared environment produces history rows that no repository explains.

06Check yourself

Two branches each add a different V7__ file. Git merges both cleanly. What does Flyway do at the next startup?

Flyway reports Found more than one migration with version 7 and stops. It applies nothing and corrupts nothing. Renumber the migration that has not yet run on a shared environment.

Your database is at version 8. Someone merges a V7__ from an older branch. With default settings, what happens?

out-of-order defaults to false, so Flyway reports Detected resolved migration not applied to database: 7. Renumber version 7 to the next free version rather than enabling out-of-order execution.

Which CI check gives the most confidence in a migration?

Applying the full sequence from empty executes the SQL and proves the ordering. Filename and parse checks inspect text only; they cannot detect a migration that references a column a later migration creates.
