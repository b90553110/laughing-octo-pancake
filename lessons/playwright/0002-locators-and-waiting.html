Locators and waiting

How you find an element decides whether your suite survives the next refactor. This is the highest-leverage decision in the track.

~20 minutes · Playwright 1.63.0 · Angular 22 · Angular Material
I did not execute this code. Report any behaviour that differs.

Most end-to-end suites die the same way: a developer restructures a component, forty tests fail, nobody can tell which failures indicate real bugs, and the suite gets marked skipped. The cause is almost always the locators.

A locator that describes the DOM structure breaks when the structure changes. A locator that describes what the user sees breaks when the user-visible behaviour changes — which is precisely when a test should fail.

01The priority order

Work down this list and stop at the first option that fits:

1. getByRole('button', { name: 'Save' })   ← default choice
2. getByLabel('Email')                     ← form fields
3. getByPlaceholder('Search users')
4. getByText('No results found')           ← non-interactive text
5. getByTestId('user-row')                 ← deliberate escape hatch
6. locator('.mat-mdc-button')              ← last resort

Compare the two styles directly:

// Brittle. Every one of these breaks on a refactor
// that changes nothing a user can perceive.
page.locator('.mat-mdc-raised-button.mat-primary')
page.locator('app-register-form > div > form > button:nth-child(3)')
page.locator('//div[@id="main"]/app-user-list/table/tbody/tr[2]')
// Durable. Each describes what the user sees.
page.getByRole('button', { name: 'Create account' })
page.getByLabel('Email')
page.getByRole('row', { name: 'ada@example.test' })
The secondary benefit

A role-based locator cannot find a control that has no accessible name. That gap is usually a real accessibility defect — an icon button with no aria-label, an input with no associated label. Writing role-based locators surfaces those defects as a side effect, and fixing them improves the product rather than only the test.

02Angular Material exposes roles already

Angular Material components render correct ARIA roles without any work from you. Use them instead of reaching for the generated class names, which change between Material versions.

// Angular Material renders semantic roles. Use them.
// <button mat-raised-button>Create account</button>
page.getByRole('button', { name: 'Create account' })

// <mat-select> exposes role="combobox", options role="option"
await page.getByRole('combobox', { name: 'Country' }).click();
await page.getByRole('option', { name: 'Portugal' }).click();

// <mat-dialog> exposes role="dialog". Scope inside it:
const dialog = page.getByRole('dialog', { name: 'Confirm deletion' });
await dialog.getByRole('button', { name: 'Delete' }).click();
Constraint

Never target a .mat-mdc-* class. Those names encode Material's internal implementation and Angular has renamed them across major versions. A suite pinned to them breaks on a dependency upgrade that changed nothing users can see.

03Strict mode

A Playwright locator that matches more than one element fails rather than guessing:

// Two "Delete" buttons on the page:
await page.getByRole('button', { name: 'Delete' }).click();

// Error: strict mode violation: getByRole('button', { name: 'Delete' })
// resolved to 2 elements

Treat this error as a design signal, not an obstacle. It means your description was ambiguous, and .first() resolves the ambiguity by picking an arbitrary element — which is how a test starts deleting the wrong user after a sort order changes.

Resolve ambiguity by narrowing the context instead:

// Fix by scoping, not by picking an index.
const row = page.getByRole('row', { name: 'ada@example.test' });
await row.getByRole('button', { name: 'Delete' }).click();

// Or filter explicitly:
await page.getByRole('listitem')
          .filter({ hasText: 'Ada Lovelace' })
          .getByRole('button', { name: 'Delete' })
          .click();
In review

Reject .first(), .last() and .nth(n) unless the test is genuinely about position — "the first row is the newest". Every other use hides an ambiguity that will resolve differently one day.

04Web-first assertions

Playwright's expect retries. That property is what lets you delete every manual wait:

// Web-first: each retries until it passes or times out.
await expect(page.getByRole('alert')).toBeVisible();
await expect(page.getByRole('row')).toHaveCount(3);
await expect(page.getByLabel('Email')).toHaveValue('ada@example.test');
await expect(page).toHaveURL(/\/users\/\d+/);

// NOT web-first: evaluates once, no retry. A race.
expect(await page.getByRole('alert').isVisible()).toBe(true);

Note the final line carefully. Calling await locator.isVisible() and asserting on the boolean evaluates the page once. No retry happens, so the assertion runs against whatever the DOM held at that instant. That single pattern accounts for a large share of flaky Playwright tests.

The distinction to memorise

await expect(locator).toBeVisible() retries. expect(await locator.isVisible()).toBe(true) does not. Put the await before expect, never inside it.

05When nothing semantic fits

Some elements carry no role and no label — a status region, a computed total. Add an explicit test hook rather than falling back to a CSS path:

<!-- When no role or label fits, add an explicit hook -->
<div data-testid="user-row-total">42 users</div>

A data-testid is a contract: it exists for tests, and a developer who sees it knows that renaming it breaks something. A class name carries no such signal, which is why someone will eventually rename it during a styling change.

Order of preference, restated

Prefer a role. Add an accessible name to the component when the role alone is ambiguous — that improves the product. Add a data-testid when no semantic option exists. Reach for CSS only when you cannot modify the component, and record why in a comment.

06Check yourself

Which locator should you reach for first?

Role plus accessible name describes what the user perceives, so it survives DOM and styling changes. getByTestId is the deliberate escape hatch when nothing semantic fits; CSS and XPath come last.

What does auto-waiting remove from your tests?

Before acting, Playwright waits for the element to be attached, visible, stable, enabled and able to receive events. Assertions still matter — web-first assertions are how you express a wait correctly.

Your locator matches two elements. What does Playwright do?

Strict mode refuses to guess. Fix the ambiguity by scoping the locator inside a row, dialog or list item, rather than by adding .first().
