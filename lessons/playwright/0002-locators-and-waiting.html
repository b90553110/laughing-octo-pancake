Locators and waiting

How a test finds an element determines whether it still works after someone refactors the application. This is the most consequential decision in the track.

~20 minutes · Playwright 1.63.0 · Angular 22 · Angular Material
I did not execute the code in this lesson. Please report anything that behaves differently.

End-to-end suites usually become unusable in the same way. A developer restructures a component, a large number of tests fail at once, nobody can work out which of those failures represent real bugs, and the team marks the suite as skipped. In most cases the locators are what caused it.

The reason is straightforward. A locator that describes the structure of the DOM breaks whenever that structure changes, including changes that make no difference to anyone using the application. A locator that describes what the user can see only breaks when the user-visible behaviour changes, which is exactly when you want a test to fail.

01The priority order

Work down this list and use the first option that fits the element you need:

1. getByRole('button', { name: 'Save' })   ← default choice
2. getByLabel('Email')                     ← form fields
3. getByPlaceholder('Search users')
4. getByText('No results found')           ← non-interactive text
5. getByTestId('user-row')                 ← deliberate escape hatch
6. locator('.mat-mdc-button')              ← last resort

The difference between the two approaches is easier to see side by side:

// Fragile. Each of these breaks when someone refactors
// the markup without changing anything a user can see.
page.locator('.mat-mdc-raised-button.mat-primary')
page.locator('app-register-form > div > form > button:nth-child(3)')
page.locator('//div[@id="main"]/app-user-list/table/tbody/tr[2]')
// Durable. Each describes something the user can see.
page.getByRole('button', { name: 'Create account' })
page.getByLabel('Email')
page.getByRole('row', { name: 'ada@example.test' })
A useful side effect

If a control has no accessible name, a role-based locator cannot find it. That gap is usually a genuine accessibility problem, such as an icon button with no aria-label or an input with no associated label. Writing locators this way tends to surface those problems, and fixing them improves the application rather than only the test.

02Angular Material already exposes roles

Angular Material components render appropriate ARIA roles without any extra work on your part, so you can target those roles instead of the generated class names.

// Angular Material renders semantic roles. Use them.
// <button mat-raised-button>Create account</button>
page.getByRole('button', { name: 'Create account' })

// <mat-select> exposes role="combobox", options role="option"
await page.getByRole('combobox', { name: 'Country' }).click();
await page.getByRole('option', { name: 'Portugal' }).click();

// <mat-dialog> exposes role="dialog". Scope inside it:
const dialog = page.getByRole('dialog', { name: 'Confirm deletion' });
await dialog.getByRole('button', { name: 'Delete' }).click();
Avoid the generated class names

Do not write locators that target .mat-mdc-* classes. Those names describe Material's internal implementation, and Angular has renamed them between major versions. A suite that depends on them will break during a dependency upgrade that changed nothing users can see.

03Strict mode

When a locator matches more than one element, Playwright reports an error rather than choosing one:

// Two "Delete" buttons on the page:
await page.getByRole('button', { name: 'Delete' }).click();

// Error: strict mode violation: getByRole('button', { name: 'Delete' })
// resolved to 2 elements

It is worth treating this error as useful information rather than an obstacle. It tells you the description was ambiguous. Adding .first() resolves the ambiguity by picking an arbitrary element, which is how a test ends up deleting the wrong user once the sort order changes.

A better fix is to narrow the area the locator searches:

// Narrow the search area rather than picking an index.
const row = page.getByRole('row', { name: 'ada@example.test' });
await row.getByRole('button', { name: 'Delete' }).click();

// Or filter explicitly:
await page.getByRole('listitem')
          .filter({ hasText: 'Ada Lovelace' })
          .getByRole('button', { name: 'Delete' })
          .click();
In review

Question any use of .first(), .last() or .nth(n) unless the test is genuinely about position, such as checking that the newest item appears at the top of a list. In other cases these methods conceal an ambiguity that will eventually resolve to a different element.

04Web-first assertions

Playwright's expect retries its condition, which is what allows you to remove manual waits from a test:

// Web-first: each retries until it passes or times out.
await expect(page.getByRole('alert')).toBeVisible();
await expect(page.getByRole('row')).toHaveCount(3);
await expect(page.getByLabel('Email')).toHaveValue('ada@example.test');
await expect(page).toHaveURL(/\/users\/\d+/);

// NOT web-first: evaluates once, no retry. A race condition.
expect(await page.getByRole('alert').isVisible()).toBe(true);

The last line in that example deserves a closer look, because it behaves differently from the ones above it. Calling await locator.isVisible() and then asserting on the boolean result checks the page only once, so nothing retries, and the assertion runs against whatever the page happened to contain at that instant. This pattern is responsible for a large share of flaky Playwright tests.

The distinction worth remembering

await expect(locator).toBeVisible() retries the condition, whereas expect(await locator.isVisible()).toBe(true) does not. The await belongs before expect rather than inside it.

05When nothing semantic fits

Some elements have no useful role and no label, such as a status region or a computed total. For those, add an explicit hook for tests rather than falling back to a CSS path:

<!-- When no role or label fits, add an explicit hook -->
<div data-testid="user-row-total">42 users</div>

A data-testid attribute acts as a contract. It exists for the tests, and a developer who encounters it can see that renaming it will break something. A class name carries no such signal, so sooner or later someone renames it while changing the styling.

The order of preference, restated

Use a role where one fits. Where the role alone is ambiguous, add an accessible name to the component, which improves the application as well as the test. Add a data-testid when no semantic option exists. Fall back to CSS only when you cannot change the component, and leave a comment explaining why.

06Check yourself

Which locator should you reach for first?

A role combined with an accessible name describes what the user perceives, so it survives changes to the DOM and the styling. getByTestId is the deliberate fallback when nothing semantic fits, and CSS and XPath come last.

What does auto-waiting remove from your tests?

Before acting on an element, Playwright waits for it to be present, visible, stable, enabled and able to receive the action. Assertions are still necessary, and web-first assertions are how you express a wait correctly.

Your locator matches two elements. What does Playwright do?

Strict mode reports the ambiguity instead of guessing. The right fix is to scope the locator inside the relevant row, dialog or list item, rather than adding .first().
