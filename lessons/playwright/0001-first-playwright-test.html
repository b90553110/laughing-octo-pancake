Your first Playwright test

Install the runner, let it start Angular for you, and write one test that survives a redeploy.

~20 minutes · Playwright 1.63.0 · Angular 22 · TypeScript
Versions verified against the npm registry on 15 September 2026. I did not execute this code.

This track starts a second subject. It shares nothing with the Spring track except the discipline: verify behaviour, and write tests that fail only when the application breaks.

That second clause is the whole difficulty. An end-to-end suite that fails randomly gets ignored, then deleted. Every decision in this track optimises against flakiness, starting with the two that matter most: how Playwright waits, and how you find elements.

01Install

Run this in your Angular project root:

npm init playwright@latest

# Answers for an Angular project:
#   TypeScript            → yes
#   Tests folder          → e2e   (not "tests": Angular uses that name)
#   GitHub Actions        → your call
#   Install browsers      → yes
Name the folder e2e

Playwright proposes tests/. Angular's own unit tests already live under src/, and a top-level tests/ invites confusion about which runner owns which file. Choose e2e/ and the boundary stays obvious to everyone.

my-angular-app/
├── e2e/
│   └── example.spec.ts
├── playwright.config.ts
├── angular.json
└── package.json

The installer downloads browser binaries into a cache outside your project. Those binaries are version-matched to the Playwright release, which is why upgrading Playwright requires npx playwright install again.

02Configure

Edit playwright.config.ts. Four settings earn their place immediately:

playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',

  // Fail the build if a test.only reaches CI.
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,

  use: {
    baseURL: 'http://localhost:4200',
    // Keep a trace from the first retry of a failing test.
    trace: 'on-first-retry',
  },

  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],

  // Playwright starts Angular itself, then shuts it down.
  webServer: {
    command: 'ng serve',
    url: 'http://localhost:4200',
    reuseExistingServer: !process.env.CI,
    timeout: 120_000,
  },
});
  • webServer — Playwright runs ng serve, waits for port 4200 to answer, runs the tests, then stops the server. Locally, reuseExistingServer attaches to a dev server you already have running instead of starting a second one.
  • baseURL — lets tests call page.goto('/register'). Point it at a deployed environment through an environment variable and the same suite runs against staging unchanged.
  • trace: 'on-first-retry' — the most valuable setting in the file. See §04.
  • forbidOnly — a stray test.only silently reduces CI to one test. This setting turns that mistake into a build failure.

03Write the test

e2e/register.spec.ts
import { test, expect } from '@playwright/test';

test('registers a user', async ({ page }) => {
  await page.goto('/register');

  await page.getByLabel('Email').fill('ada@example.test');
  await page.getByLabel('Display name').fill('Ada Lovelace');
  await page.getByRole('button', { name: 'Create account' }).click();

  await expect(page.getByRole('heading', { name: 'Welcome, Ada' }))
    .toBeVisible();
});

Read what this test does not contain. No waits. No sleeps. No CSS selectors. No check that the button exists before clicking it.

Auto-waiting removes all of it. Before clicking, Playwright waits for the element to be attached, visible, stable, enabled, and able to receive events. It retries until the element passes every check or the timeout expires. Angular's rendering cycle therefore needs no special handling: an element that has not rendered yet is one Playwright is still waiting for.

expect(locator).toBeVisible() works the same way. It retries until the assertion passes or times out, which is why the last line needs no wait either.

The rule that prevents most flakiness

Never call page.waitForTimeout() in a test. A fixed sleep is either too short, which makes the test flaky, or too long, which makes the suite slow — and it is usually both on different machines. Every legitimate wait is expressible as an assertion about page state.

04Run, and read a failure

npx playwright test                 # all tests, headless
npx playwright test --ui           # interactive runner; use while writing
npx playwright test --headed       # watch a real browser
npx playwright test e2e/register   # one file
npx playwright show-report         # open the last HTML report
npx playwright codegen localhost:4200   # record actions into code

Use --ui while writing tests. It shows every action, the DOM at each step, and lets you re-run a single test without restarting Angular.

When a test fails in CI, open the trace. A trace records a DOM snapshot before and after every action, the network calls, the console output, and the source line for each step. It turns "flaky in CI, passes locally" from a guess into an observation: you see the exact DOM at the moment the click missed.

Why on-first-retry

Tracing every run costs time and disk. on-first-retry records nothing while tests pass, and produces a full trace the moment one fails and retries. You get the diagnostic exactly when you need it and pay nothing the rest of the time.

05What to test at this level

End-to-end tests are the slowest and most fragile tests you own. Spend them deliberately.

  • Test the handful of journeys that generate revenue or block users. Registration, login, checkout, the primary create-and-save path. Ten solid journeys beat two hundred shallow ones.
  • Push everything else down. Component behaviour belongs in Angular's own component tests, which run in a fraction of the time.
  • Never assert on styling or exact copy unless the product requires that exact string. Both change for reasons unrelated to correctness.
In review

A pull request that adds twenty end-to-end tests is a problem, not progress. Ask which layer each test belongs to. The suite's value falls the moment its runtime or its failure rate makes the team stop reading the results.

06Check yourself

What does npx playwright test do by default?

It runs headless across every project in the config, in parallel. Add --headed to watch a browser, or --ui for the interactive runner.

What does a Playwright trace contain?

A trace holds DOM snapshots before and after each action, network activity, console output and the source line per step. It is the tool that explains a CI-only failure.

What does the webServer config block do?

Playwright runs the command, waits for the URL to respond, runs the tests, then shuts the server down. reuseExistingServer attaches to a dev server you already started locally.
