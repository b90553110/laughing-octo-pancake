Your first Playwright test

Install the test runner, configure it to start Angular for you, and write a test that keeps working after the application changes.

~20 minutes · Playwright 1.63.0 · Angular 22 · TypeScript
I verified the versions against the npm registry on 15 September 2026, but I did not execute the code in this lesson.

This track covers end-to-end testing, which has little in common with the Spring track apart from a shared concern: a test should fail when the application breaks, and at no other time.

That second part is the difficult one. When an end-to-end suite fails for reasons unrelated to the application, people stop trusting the results, then stop reading them, and eventually delete the suite. Two things determine whether that happens to you: how the test waits for the page, and how it finds elements. This lesson covers waiting, and lesson 02 covers finding elements.

01Install

Run the installer in the root of your Angular project:

npm init playwright@latest

# Answers for an Angular project:
#   TypeScript            → yes
#   Tests folder          → e2e   (not "tests": Angular uses that name)
#   GitHub Actions        → your call
#   Install browsers      → yes
Name the folder e2e

The installer suggests tests/ as the folder name. Angular's own unit tests already live under src/, so a second folder called tests/ makes it unclear which runner owns which file. Calling the folder e2e/ keeps that boundary obvious to the next person who opens the project.

my-angular-app/
├── e2e/
│   └── example.spec.ts
├── playwright.config.ts
├── angular.json
└── package.json

The installer also downloads browser binaries into a cache outside your project. Playwright matches those binaries to the library version, which is why you need to run npx playwright install again after upgrading Playwright.

02Configure

Open playwright.config.ts. Four settings are worth adding straight away, and the list below explains each one.

playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',

  // Fail the build if a test.only reaches CI.
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,

  use: {
    baseURL: 'http://localhost:4200',
    // Keep a trace from the first retry of a failing test.
    trace: 'on-first-retry',
  },

  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
  ],

  // Playwright starts Angular itself, then shuts it down.
  webServer: {
    command: 'ng serve',
    url: 'http://localhost:4200',
    reuseExistingServer: !process.env.CI,
    timeout: 120_000,
  },
});
  • webServer tells Playwright to run ng serve itself. Playwright waits for port 4200 to respond, runs the tests, and then stops the server. Locally, reuseExistingServer attaches to a dev server you already have running instead of starting a second one.
  • baseURL lets a test call page.goto('/register') rather than repeating the host in every test. If you set it from an environment variable, the same suite can run against a deployed environment without any other change.
  • trace: 'on-first-retry' controls what Playwright records when a test fails. Section 04 explains why this setting matters more than the others.
  • forbidOnly turns a test.only that reaches CI into a build failure. Without it, a test.only left in by accident quietly reduces your whole CI run to a single test.

03Write the test

e2e/register.spec.ts
import { test, expect } from '@playwright/test';

test('registers a user', async ({ page }) => {
  await page.goto('/register');

  await page.getByLabel('Email').fill('ada@example.test');
  await page.getByLabel('Display name').fill('Ada Lovelace');
  await page.getByRole('button', { name: 'Create account' }).click();

  await expect(page.getByRole('heading', { name: 'Welcome, Ada' }))
    .toBeVisible();
});

The interesting thing about this test is what it leaves out. There are no explicit waits, no sleeps, no CSS selectors, and no check that the button exists before the test clicks it.

Playwright can leave all of that out because of a feature called auto-waiting. Before it clicks an element, Playwright waits for that element to be present in the page, visible, stable, enabled, and able to receive the click. It keeps retrying those checks until they all pass or the timeout expires. Angular's rendering therefore needs no special handling, because an element that Angular has not rendered yet is an element Playwright is still waiting for.

Assertions behave the same way. expect(locator).toBeVisible() retries until the condition holds or the timeout expires, so the final line of the test needs no wait either.

The rule that prevents most flaky tests

Do not call page.waitForTimeout() in a test. A fixed sleep is either shorter than the operation, which makes the test fail intermittently, or longer than it needs to be, which makes the suite slow. On a mixture of developer laptops and CI machines it is usually both. Any wait you need can be expressed as an assertion about the state of the page instead.

04Run the tests and read a failure

npx playwright test                 # all tests, headless
npx playwright test --ui           # interactive runner; use while writing
npx playwright test --headed       # watch a real browser
npx playwright test e2e/register   # one file
npx playwright show-report         # open the last HTML report
npx playwright codegen localhost:4200   # record actions into code

While you are writing tests, run them with --ui. The interactive runner shows every action the test takes, lets you inspect the page at each step, and re-runs a single test without restarting Angular.

When a test fails in CI, open its trace. A trace records a snapshot of the page before and after every action, along with the network requests, the console output, and the line of test code responsible for each step. This is what turns "it fails in CI but passes locally" from a guess into something you can look at directly, because you can see the state of the page at the moment the click went to the wrong place.

Why on-first-retry rather than every run

Recording a trace for every test run costs both time and disk space. The on-first-retry setting records nothing while tests pass, and produces a complete trace as soon as a test fails and Playwright retries it. You get the diagnostic information when you need it without paying for it the rest of the time.

05Deciding what to test at this level

End-to-end tests are slower and more sensitive to change than any other kind of test in your project, so it is worth being selective about what you cover with them.

  • Cover the small number of journeys that matter most, such as registration, logging in, checkout, or whatever your main create-and-save path is. Ten reliable journey tests are more useful than two hundred shallow ones.
  • Test component behaviour further down. Angular's own component tests run in a fraction of the time and give clearer failures for that kind of problem.
  • Avoid asserting on styling or on exact wording unless the product depends on that exact text, because both change for reasons that have nothing to do with whether the application works.
In review

When a pull request adds twenty end-to-end tests at once, ask which layer each test belongs in. A suite loses its value as soon as its runtime or its failure rate persuades the team to stop reading the results, and adding many shallow tests is the usual way that happens.

06Check yourself

What does npx playwright test do by default?

It runs the tests headless and in parallel, across every project listed in the configuration. Add --headed to watch a browser, or --ui for the interactive runner.

What does a Playwright trace contain?

A trace holds a snapshot of the page before and after each action, together with network activity, console output, and the line of test code for each step. It is the most useful tool available when a test fails only in CI.

What does the webServer config block do?

Playwright runs the command you give it, waits for the URL to respond, runs the tests, and then shuts the server down. Setting reuseExistingServer makes it attach to a dev server you already started locally.
