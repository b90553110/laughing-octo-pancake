Iterating on migrations in development

Schema design changes twenty times before it is right. Flyway's immutability rule applies to shared environments, not to your laptop.

~20 minutes · Flyway 12.4.0 · Spring Boot 4.1.1
Property defaults read from FlywayProperties.java in the Spring Boot sources jar. I did not execute this code.

New engineers apply the rule from Lesson 02 too widely. They write a migration, find a mistake ten minutes later, and add a second migration to correct the first. After two days the branch contains six migrations describing one schema change, and the review is unreadable.

Read the rule precisely: never modify a migration that has run on any machine other than your own. A migration on an unmerged branch has run only on your machine. Edit it freely.

01The development loop

Editing the file is the easy half. Your local database already recorded the old checksum, so the next startup fails validation. You need to discard the local database state, and three mechanisms exist. They differ in risk.

Rebuild the database — use this one

Destroy the container and recreate it. Flyway then applies your edited migration from empty, which is exactly what CI and every fresh environment will do.

docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: demo
      POSTGRES_USER: demo
      POSTGRES_PASSWORD: demo
    ports: ["5432:5432"]
reset the database
# Destroy the database and rebuild it from migrations.
docker compose down -v && docker compose up -d db
./mvnw spring-boot:run
Recommendation

Make this one command and put it in the README. The whole workflow depends on rebuilding being cheap: an engineer who finds it tedious will start editing the shared database by hand, and the repository stops describing the schema. Optimise the reset, not the workaround.

flyway clean — narrower, and disabled by default

clean drops every object in the configured schemas. Spring Boot sets spring.flyway.clean-disabled to true, so the command fails until you enable it explicitly:

application-dev.properties
# application-dev.properties — LOCAL DEVELOPMENT ONLY
spring.flyway.clean-disabled=false
Constraint

Set this property in a development-profile file only, never in application.properties. A build that carries clean-disabled=false into an environment whose datasource points at a shared database is one configuration mistake away from deleting it. Rebuilding a container carries no equivalent risk, which is why §01 recommends it instead.

repair — the wrong tool here

repair overwrites stored checksums to match your files. It does not re-run the edited SQL, so your database keeps the schema the old version of the migration produced while the history table claims the new one ran. You then develop against a schema that exists on no other machine. Do not use repair to iterate.

02Squash before you merge

Your branch's migration history is working material, not a record anyone needs. Collapse it into the migration you actually intend to ship:

# Before: your branch, after two days of iteration
V20260915103000__add_users_phone.sql
V20260915141500__fix_users_phone_type.sql
V20260916091200__add_users_phone_index.sql

# After: one migration describing the end state
V20260916091200__add_users_phone.sql

Reviewers then read one file describing the end state rather than reconstructing it from three diffs. Squash while the migrations remain local; once any of them merges, Lesson 02's rule applies and you add a new migration instead.

Check before squashing

Confirm no shared environment applied the intermediate migrations. A review app or a shared development database that tracks your branch counts as a shared environment. When one exists, keep the sequence and rebuild that environment from empty.

03Seed data belongs in a separate location

Development needs rows: a few users to click through, an order to render. Those rows must never reach production, so keep them out of db/migration entirely and add a second location under the development profile.

application-dev.properties
# application-dev.properties
# Load the schema, then development-only seed data.
spring.flyway.locations=classpath:db/migration,classpath:db/dev-seed
src/main/resources/db/dev-seed/R__dev_users.sql
-- src/main/resources/db/dev-seed/R__dev_users.sql
-- Repeatable: re-runs whenever its checksum changes.

DELETE FROM users WHERE email LIKE '%@example.test';

INSERT INTO users (email, display_name) VALUES
  ('ada@example.test',   'Ada Lovelace'),
  ('grace@example.test', 'Grace Hopper');

The R__ prefix marks a repeatable migration. Flyway runs repeatable migrations after all versioned migrations, and re-runs each one whenever its checksum changes. Seed data therefore updates when you edit the file, with no version number to manage. Make the script idempotent — the DELETE above does that — because Flyway will run it more than once.

Constraint

Production configuration must never list classpath:db/dev-seed. Verify this by starting the application with the production profile and confirming the log reports only your versioned migrations.

04When a shared development database diverges

A shared development database accumulates manual changes, abandoned branches and partially applied migrations. Three settings address three distinct situations. Match the setting to the situation precisely.

  • The database predates Flyway and already holds tables. Flyway reports Found non-empty schema(s) without schema history table. Set spring.flyway.baseline-on-migrate=true and baseline-version to the version the existing schema represents. Flyway records the baseline and applies only later migrations. Run this once, deliberately, then remove the setting.
  • A migration failed partway. Flyway reports Detected failed migration. Fix the SQL, manually revert whatever the partial run left behind, then run repair to remove the failed row. PostgreSQL runs DDL transactionally, so this is rarer there than on MySQL.
  • Someone edited an applied migration and the change is genuinely cosmetic. Run repair. This is the only legitimate use of the command.
Recommendation

Give every engineer a disposable local database and stop sharing one. A shared development database creates a schema whose state depends on who ran what, which is the problem Flyway exists to solve. Where a shared environment is unavoidable, rebuild it from empty on a schedule and treat any manual change to it as a defect.

One default worth knowing

Spring Boot sets spring.flyway.ignore-migration-patterns to *:future. Flyway therefore tolerates a database that holds migrations newer than the files present — the state produced by rolling an application back without rolling back its schema. Startup succeeds rather than failing, which is the behaviour you want during a rollback.

05Practices

  • Edit freely before merge; add a migration after. The boundary is the first machine that is not yours.
  • Rebuild from empty before opening a pull request. This catches a migration that works only against your accumulated local state.
  • Keep the reset to one command. Tedious resets produce hand-edited databases.
  • Separate seed data from schema by location, not by convention. A comment saying "development only" will eventually run in production.
  • Write every repeatable migration to be idempotent. Flyway re-runs it on every checksum change.
  • Treat clean and repair as incident tools. Neither belongs in a daily loop. Rebuilding replaces both.

06Check yourself

You wrote a migration this morning on an unmerged branch. May you edit the file?

The rule protects databases you do not control. A migration that has run only on your machine has no other history table recording its checksum, so editing it costs nothing.

You edited that migration. Your local database still holds the old version. What is the correct next step?

Rebuilding applies the edited SQL from empty, matching what CI and every fresh environment will do. repair only updates the checksum: the database keeps the schema the old SQL produced while the history table claims otherwise.

What value does Spring Boot use for spring.flyway.clean-disabled?

FlywayProperties declares private boolean cleanDisabled = true;. Spring Boot blocks clean in every profile until you set the property to false explicitly. Several third-party articles state the opposite; they describe Flyway's standalone default, not Spring Boot's.
