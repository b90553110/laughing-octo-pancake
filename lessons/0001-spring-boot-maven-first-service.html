Workspace · Lesson 01

Your first Spring Boot service

One HTTP endpoint, built with Maven, running on your machine and covered by a test — and an honest account of what each file is doing.

~20 minutes · Spring Boot 4.1.1 · Java 21 · Maven 3.9.11
Every command below was run end-to-end before this lesson was written.

You know Java. That means almost nothing here is new language — the new part is that you stop calling your code, and something else calls it for you. That inversion is the whole of Spring, and everything else is detail.

By the end you will have a service that answers GET /hello, and you will be able to say what every line in your pom.xml is for. That second half is the part that matters to me as your lead: people who can only regenerate a project from a website are stuck the first time the build breaks.

01Check your tools

Two things must be installed. Run both:

java -version
mvn -v

What you need, from the official requirements for this version: Spring Boot 4.1.1 needs Java 17 or newer (it is tested up to Java 26), and the Spring Boot Maven plugin needs Maven 3.6.3 or newer — though Maven itself now treats 3.9.0 as the floor for new plugin releases, so use 3.9+ and avoid a class of strange errors.1,3

Tech lead note

Pick a Long Term Support Java version — 17, 21 or 25 — not the newest one. Non-LTS releases stop getting patches after six months, and you do not want your service's security posture tied to a version nobody ships fixes for. I used 21 here.

02Generate the skeleton

Nobody writes a Spring Boot project from an empty directory, and you should not either. Go to start.spring.io and choose:

  • Project: Maven
  • Language: Java
  • Spring Boot: the latest non-SNAPSHOT, non-M version (4.1.1 at time of writing)
  • Java: 21
  • Dependencies: Spring Web — that one, nothing else, for now

Hit Generate, unzip it, open it. You get this:

demo/
├── pom.xml                    ← the build. Start here.
├── mvnw, mvnw.cmd             ← Maven wrapper: pins Maven per-project
└── src/
    ├── main/
    │   ├── java/com/example/demo/DemoApplication.java
    │   └── resources/application.properties
    └── test/
        └── java/com/example/demo/DemoApplicationTests.java
Why so few files

Spring Boot's entire pitch is that configuration you did not write is configuration you cannot get wrong. An equivalent Java web app in 2010 would have started with several hundred lines of XML. That is what "auto-configuration" bought.

03Read the pom.xml

This is the file to actually understand. Maven reads it to answer two questions: what does this project depend on, and how is it built.

pom.xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0" ...>
  <modelVersion>4.0.0</modelVersion>

  <!-- 1. Inherit sane defaults + a tested dependency list -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
    <relativePath/>
  </parent>

  <!-- 2. Who this artifact is -->
  <groupId>com.example</groupId>
  <artifactId>demo</artifactId>
  <version>0.0.1-SNAPSHOT</version>

  <properties>
    <java.version>21</java.version>
  </properties>

  <!-- 3. What you depend on. Note: no version numbers. -->
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <!-- 4. The plugin that makes "one runnable jar" work -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>

Four things are happening, and the numbered comments map to them:

  1. The parent. Your project inherits from spring-boot-starter-parent. Its job is a giant, tested list of "if you use library X, use exactly version Y" — every Spring library, plus Jackson, Tomcat, JUnit, Logback and hundreds more, all versions known to work together.
  2. Coordinates. groupId + artifactId + version uniquely name your artifact, the same way every dependency below is named.
  3. Dependencies, with no version numbers. This is the payoff from (1). A starter is a curated bundle: spring-boot-starter-web pulls in Spring MVC, JSON handling, and an embedded Tomcat, because you asked for "web" rather than for nine libraries by name.
  4. The plugin. spring-boot-maven-plugin repackages your compiled classes plus every dependency into a single runnable jar.
Tech lead note

When you review a pom.xml and see an explicit <version> on a Spring dependency, ask why. Usually someone pinned a version to fix one bug and silently desynchronised it from the rest of the set. That is a genuine source of 3am incidents.

04The application class

It was generated for you. It is three meaningful lines:

src/main/java/com/example/demo/DemoApplication.java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@SpringBootApplication is three annotations in a trench coat:

  • @SpringBootConfiguration — this class can define beans
  • @EnableAutoConfiguration — look at what is on the classpath and configure it. Tomcat is on the classpath, so start a web server.
  • @ComponentScan — scan this package and everything below it for classes to manage
The one layout rule

Because of @ComponentScan, your application class must sit in the top package, with all other code beneath it. Put a controller in a sibling package and Spring will not find it, and you will get a 404 with no error at startup. This is the single most common way a first Spring project goes quietly wrong.

05Add an endpoint

New file, next to DemoApplication.java:

src/main/java/com/example/demo/GreetingController.java
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class GreetingController {

    @GetMapping("/hello")
    public String hello(@RequestParam(defaultValue = "world") String name) {
        return "Hello, " + name + "!";
    }
}

You never construct GreetingController. At startup, component scanning finds it, Spring creates one instance, and registers /hello in a routing table. That is the inversion: your class is a thing that gets called, not a thing that runs.

06Run it

Do this 
./mvnw spring-boot:run

Then, in another terminal:

curl localhost:8080/hello
curl "localhost:8080/hello?name=Ada"

You should see Hello, world! and Hello, Ada!. In the startup log, the line worth reading is:

Tomcat started on port 8080 (http) with context path '/'
Started DemoApplication in 1.691 seconds

You did not install Tomcat, configure it, or deploy anything to it. It arrived as a dependency of the web starter and was started by auto-configuration.

./mvnw vs mvn

Use ./mvnw — the Maven wrapper script in your project. It downloads and uses the exact Maven version the project expects, so your machine, your teammate's machine and CI all build identically. mvn uses whatever happens to be installed.

07Test it

An endpoint with no test is a demo, not a service. Add one:

src/test/java/com/example/demo/GreetingControllerTest.java
package com.example.demo;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

// Spring Boot 4 moved this out of spring-boot-test-autoconfigure:
import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class GreetingControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void greetsTheWorldByDefault() throws Exception {
        mockMvc.perform(get("/hello"))
               .andExpect(status().isOk())
               .andExpect(content().string("Hello, world!"));
    }
}

And add the module that provides those test annotations to your <dependencies>:

pom.xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-webmvc-test</artifactId>
  <scope>test</scope>
</dependency>
A real trap, hit while writing this

Nearly every tutorial online imports @AutoConfigureMockMvc and @WebMvcTest from org.springframework.boot.test.autoconfigure.web.servlet. In Spring Boot 4 that package no longer exists — test slices were split into per-technology modules, and the class now lives in org.springframework.boot.webmvc.test.autoconfigure, supplied by spring-boot-webmvc-test. I hit exactly this compile error building this lesson. When an import that "should" work does not, suspect a version boundary before you suspect yourself.

Do this 
./mvnw test

Expected: Tests run: 1, Failures: 0, Errors: 0.

MockMvc calls your controller through the full Spring request path — routing, parameter binding, response conversion — without opening a socket. Fast enough to run on every save.

08Check yourself

Answer before you scroll back. Retrieving something is what makes it stick; re-reading mostly makes it feel familiar.

What does spring-boot-starter-parent give your build?

It is dependency management: a curated set of versions known to work together, which is why your dependencies carry no version tags. It ships no code of its own.

Your log says Tomcat started on port 8080. Where did Tomcat come from?

spring-boot-starter-web pulls in an embedded Tomcat, and auto-configuration starts it because it is on the classpath. Remove that starter and the same code runs as a plain command-line app.

An import from ...boot.test.autoconfigure.web.servlet fails to compile. Most likely cause?

Test slices moved into per-technology modules. The class kept its name and moved to org.springframework.boot.webmvc.test.autoconfigure, in the spring-boot-webmvc-test artifact you have to add.
