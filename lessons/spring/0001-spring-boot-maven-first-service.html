Workspace · Spring track · Lesson 01

Your first Spring Boot service

One HTTP endpoint, built with Maven, running on your machine and covered by a test, with an account of what each file does.

~20 minutes · Spring Boot 4.1.1 · Java 21 · Maven 3.9.11
I ran every command below end to end before writing this lesson.

You already write Java, so almost nothing here is new as a language. The new part is that you stop calling your own code and Spring calls it for you. Spring is built around that inversion, and its other features assume it.

By the end you will have a service that answers GET /hello, and you will be able to say what every line of your pom.xml does. The second half is what keeps you moving the first time the build breaks, because an engineer who can only regenerate a project from a website has nowhere to go.

01Check your tools

You need Java and Maven on your path, so run both of these commands and check the output:

java -version
mvn -v

Spring Boot 4.1.1 requires Java 17 or newer and supports versions up to Java 26. The Spring Boot Maven plugin requires Maven 3.6.3 or newer, though the Maven project now treats 3.9.0 as the floor for new plugin releases, so install 3.9 or later and avoid a class of confusing errors.1,3

Recommendation

Choose a Long Term Support release of Java, meaning 17, 21 or 25, rather than the newest version available. Non-LTS releases stop receiving patches after six months, and you do not want the security posture of your service tied to a version that no longer receives fixes. I used 21 for this lesson.

02Generate the skeleton

Start from the generator rather than an empty directory, because it produces the wrapper scripts and the test layout for you. Open start.spring.io and choose these options:

  • Project: Maven
  • Language: Java
  • Spring Boot: the latest version without a SNAPSHOT or M suffix, which was 4.1.1 when I wrote this
  • Java: 21
  • Dependencies: Spring Web, and nothing else for now

Generate the project, unzip it and open it, and you get the following layout:

demo/
├── pom.xml                    ← the build. Start here.
├── mvnw, mvnw.cmd             ← Maven wrapper: pins Maven per-project
└── src/
    ├── main/
    │   ├── java/com/example/demo/DemoApplication.java
    │   └── resources/application.properties
    └── test/
        └── java/com/example/demo/DemoApplicationTests.java
Why there are so few files

Spring Boot exists to remove configuration you would otherwise write and get wrong. The equivalent Java web application in 2010 opened with several hundred lines of XML. Removing that is what the term auto-configuration refers to.

03Read the pom.xml

This is the file worth understanding. Maven reads it to answer two questions: what this project depends on, and how to build it.

pom.xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0" ...>
  <modelVersion>4.0.0</modelVersion>

  <!-- 1. Inherit sane defaults + a tested dependency list -->
  <parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>4.1.1</version>
    <relativePath/>
  </parent>

  <!-- 2. Who this artifact is -->
  <groupId>com.example</groupId>
  <artifactId>demo</artifactId>
  <version>0.0.1-SNAPSHOT</version>

  <properties>
    <java.version>21</java.version>
  </properties>

  <!-- 3. What you depend on. Note: no version numbers. -->
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-test</artifactId>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <!-- 4. The plugin that makes "one runnable jar" work -->
  <build>
    <plugins>
      <plugin>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-maven-plugin</artifactId>
      </plugin>
    </plugins>
  </build>
</project>

Four things happen here, and the numbered comments mark each one:

  1. The parent. Your project inherits from spring-boot-starter-parent, which supplies a large, tested list of the form "if you use library X, use exactly version Y". That list covers every Spring library plus Jackson, Tomcat, JUnit, Logback and several hundred more, at versions known to work together.
  2. Coordinates. The groupId, artifactId and version name your artifact, in the same way that every dependency below names itself.
  3. Dependencies with no version numbers. This is what the parent buys you. A starter is a curated bundle, so spring-boot-starter-web brings in Spring MVC, JSON handling and an embedded Tomcat because you asked for "web" instead of naming nine libraries yourself.
  4. The plugin. spring-boot-maven-plugin repackages your compiled classes and all their dependencies into a single runnable jar.
In review

When you see an explicit <version> on a Spring dependency in a pom.xml, ask why it is there. Usually somebody pinned a version to fix one bug and left it out of step with the rest of the tested set, which is a genuine source of incidents.

04The application class

The generator wrote this for you, and it contains three meaningful lines:

src/main/java/com/example/demo/DemoApplication.java
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

@SpringBootApplication combines three annotations:

  • @SpringBootConfiguration lets this class define beans.
  • @EnableAutoConfiguration inspects the classpath and configures what it finds. Tomcat is on the classpath, so Spring starts a web server.
  • @ComponentScan scans this package and everything below it for classes to manage.
The one layout rule

Because of @ComponentScan, your application class must sit in the top package with all other code beneath it. Put a controller in a sibling package and Spring will not find it, so you get a 404 with no error at startup. This is the most common way a first Spring project goes wrong without telling you.

05Add an endpoint

Create a new file next to DemoApplication.java:

src/main/java/com/example/demo/GreetingController.java
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class GreetingController {

    @GetMapping("/hello")
    public String hello(@RequestParam(defaultValue = "world") String name) {
        return "Hello, " + name + "!";
    }
}

You never construct GreetingController yourself. At startup, component scanning finds the class, Spring creates one instance, and Spring registers /hello in a routing table. Your class is something Spring calls rather than something you run.

06Run it

Do this 
./mvnw spring-boot:run

Then, in another terminal:

curl localhost:8080/hello
curl "localhost:8080/hello?name=Ada"

You should see Hello, world! and Hello, Ada!. In the startup log, these are the lines worth reading:

Tomcat started on port 8080 (http) with context path '/'
Started DemoApplication in 1.691 seconds

You did not install Tomcat, configure it, or deploy anything to it. Tomcat arrived as a dependency of the web starter, and auto-configuration started it.

Use ./mvnw rather than mvn

./mvnw is the Maven wrapper script in your project. It downloads and uses the exact Maven version the project expects, so your machine, a teammate's machine and CI all build identically. Plain mvn uses whichever version happens to be installed.

07Test it

An endpoint without a test is a demonstration rather than a service. Add one:

src/test/java/com/example/demo/GreetingControllerTest.java
package com.example.demo;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

// Spring Boot 4 moved this out of spring-boot-test-autoconfigure:
import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.content;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

@SpringBootTest
@AutoConfigureMockMvc
class GreetingControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void greetsTheWorldByDefault() throws Exception {
        mockMvc.perform(get("/hello"))
               .andExpect(status().isOk())
               .andExpect(content().string("Hello, world!"));
    }
}

Then add the module that supplies those test annotations to your <dependencies>:

pom.xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-webmvc-test</artifactId>
  <scope>test</scope>
</dependency>
A trap I hit while writing this

Most tutorials online import @AutoConfigureMockMvc and @WebMvcTest from org.springframework.boot.test.autoconfigure.web.servlet. Spring Boot 4 removed that package and split test slices into per-technology modules, so the class now lives in org.springframework.boot.webmvc.test.autoconfigure and arrives with spring-boot-webmvc-test. I hit this compile error while building the lesson. When an import that should work does not, suspect a version boundary before you suspect yourself.

Do this 
./mvnw test

Expect Tests run: 1, Failures: 0, Errors: 0.

MockMvc calls your controller through the full Spring request path, covering routing, parameter binding and response conversion, without opening a socket. It runs fast enough to use on every save.

08Check yourself

Answer before scrolling back. Retrieving something from memory is what makes it stick, whereas re-reading mostly makes it feel familiar.

What does spring-boot-starter-parent give your build?

It supplies dependency management: a curated set of versions known to work together, which is why your dependencies carry no version tags. It ships no code of its own.

Your log says Tomcat started on port 8080. Where did Tomcat come from?

spring-boot-starter-web brings in an embedded Tomcat, and auto-configuration starts it because it sits on the classpath. Remove that starter and the same code runs as a plain command-line application.

An import from ...boot.test.autoconfigure.web.servlet fails to compile. Most likely cause?

Spring Boot 4 moved test slices into per-technology modules. The class kept its name and moved to org.springframework.boot.webmvc.test.autoconfigure, in the spring-boot-webmvc-test artifact you have to add.
