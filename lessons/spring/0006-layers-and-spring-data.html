Controller, service, repository

Three layers, one rule each. Finally, Java code that reads the users table you migrated in Lesson 02.

~25 minutes · Spring Boot 4.1.1 · Spring Data JPA · PostgreSQL
I did not execute this code. Report any output that differs on your machine.

Lesson 02 created a users table. Nothing in the application has read it since. This lesson closes that gap and answers the question every new Spring codebase raises: where does the logic go?

01The three layers

HTTP request
    │
    ▼
UserController    HTTP only: parse, delegate, serialise
    │
    ▼
UserService       business rules, transaction boundary
    │
    ▼
UserRepository    data access only
    │
    ▼
PostgreSQL        schema owned by Flyway

Each layer has exactly one responsibility:

  • Controller — translate HTTP into a method call and the result back into HTTP. It contains no business rules.
  • Service — enforce business rules and define the transaction boundary. It knows nothing about HTTP.
  • Repository — read and write rows. It enforces no rules.
The test that matters

A service must not import anything from org.springframework.web. When a service needs the HTTP request, the responsibility has leaked and the logic belongs in the controller or the parameter list. This single import rule catches most layering violations in review.

02The entity

An entity maps a Java class to a table. Flyway still owns the schema; the entity only describes what Flyway already created.

src/main/java/com/example/demo/user/User.java
package com.example.demo.user;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(name = "display_name", nullable = false)
    private String displayName;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    protected User() { }   // JPA requires a no-arg constructor.

    public User(String email, String displayName) {
        this.email = email;
        this.displayName = displayName;
        this.createdAt = Instant.now();
    }

    public Long getId()          { return id; }
    public String getEmail()     { return email; }
    public String getDisplayName() { return displayName; }
}
Constraint

Never let an entity define the schema. With ddl-auto=validate from Lesson 02, Hibernate compares this class against the real table at startup and fails on any mismatch. Adding a field here does not add a column — write a migration, then add the field. The startup failure is the mechanism that keeps the two in step.

03The repository

Declare an interface. Write no implementation.

src/main/java/com/example/demo/user/UserRepository.java
package com.example.demo.user;

import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

// You write no implementation. Spring Data generates one.
public interface UserRepository extends JpaRepository<User, Long> {

    Optional<User> findByEmail(String email);

    boolean existsByEmail(String email);
}

At startup, Spring Data JPA finds every interface extending JpaRepository and generates a proxy implementing it. Extending JpaRepository<User, Long> supplies save, findById, findAll, delete and roughly twenty more methods.

Spring Data derives the other methods from their names. It parses the name into a query at startup:

findByEmail(String email)
        → SELECT * FROM users WHERE email = ?

findByDisplayNameContainingIgnoreCase(String part)
        → SELECT * FROM users WHERE UPPER(display_name) LIKE UPPER(?)

existsByEmail(String email)
        → SELECT COUNT(*) > 0 FROM users WHERE email = ?

countByCreatedAtAfter(Instant since)
        → SELECT COUNT(*) FROM users WHERE created_at > ?
Two consequences of name-derived queries

First, a misspelled property name fails at startup, not at call time — Spring Data cannot parse the name and refuses to build the context. Treat that failure as a compile error.

Second, derived names stop scaling. A method named findByEmailAndDisplayNameOrCreatedAtAfter is unreadable. Switch to @Query with explicit JPQL once a name exceeds roughly four conditions.

04The service

The service holds the rule that the repository and controller both lack: an email registers once.

src/main/java/com/example/demo/user/UserService.java
package com.example.demo.user;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class UserService {

    private final UserRepository users;

    public UserService(UserRepository users) {
        this.users = users;
    }

    @Transactional
    public User register(String email, String displayName) {
        if (users.existsByEmail(email)) {
            throw new EmailAlreadyRegisteredException(email);
        }
        return users.save(new User(email, displayName));
    }
}

Note the constructor injection from Lesson 05: Spring supplies the generated repository proxy through the constructor, and the field is final.

The check-then-act race

existsByEmail followed by save contains a race: two concurrent requests can both pass the check before either saves. The UNIQUE constraint from the Lesson 02 migration is what actually prevents the duplicate; the check exists to produce a clear error in the normal case. Keep both. Application checks give good messages, database constraints give correctness, and only one of them survives concurrency.

05The controller

src/main/java/com/example/demo/user/UserController.java
package com.example.demo.user;

import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @PostMapping
    public UserResponse register(@RequestBody RegisterRequest request) {
        User user = userService.register(request.email(), request.displayName());
        return UserResponse.from(user);
    }
}

// Records keep the wire format separate from the entity.
record RegisterRequest(String email, String displayName) { }

record UserResponse(Long id, String email, String displayName) {
    static UserResponse from(User user) {
        return new UserResponse(
            user.getId(), user.getEmail(), user.getDisplayName());
    }
}
Never serialise entities directly

Returning User from a controller couples your public API to your database schema: a column rename becomes a breaking API change, and any field you add leaks automatically — including a password hash. The UserResponse record costs six lines and removes both problems. Reject entity-returning controllers in review.

06Package by feature

Every class above lives in com.example.demo.user. Group by feature, not by layer.

The alternative — controller/, service/, repository/ packages — looks organised and fails in practice. Every change to one feature then touches three packages, unrelated features sit adjacent, and nothing can be package-private because collaborators live elsewhere. Feature packages keep a change in one directory and let you hide internals.

07Check yourself

Who writes the implementation of UserRepository?

Spring Data finds interfaces extending JpaRepository and generates an implementation at startup, deriving each custom query from its method name.

Where do business rules belong?

The service enforces rules and owns the transaction boundary. The controller translates HTTP only; the repository reads and writes rows only.

You declare Optional<User> findByEmail(String email). How does Spring Data handle it?

Spring Data parses the method name into a query at startup. A name referencing a property the entity lacks fails startup, so treat the parse failure as a compile error.
