Beans and dependency injection

Spring constructs your objects and hands them their dependencies. Understand that exchange and the rest of the framework follows.

~20 minutes · Spring Boot 4.1.1 · Java 21

Lesson 01 stated the inversion without explaining the mechanism: you stop calling your code, and Spring calls it instead. This lesson supplies the mechanism.

Every Spring concept you meet later — transactions, security, caching, the repositories in Lesson 06 — depends on Spring owning the object graph. Learn the exchange once here.

01What a bean is

A bean is an object that Spring constructs, holds, and supplies to whatever needs it. Spring stores every bean in the ApplicationContext, a registry it builds at startup and keeps for the lifetime of the process.

Mark a class as a bean with a stereotype annotation:

src/main/java/com/example/demo/GreetingService.java
package com.example.demo;

import org.springframework.stereotype.Service;

@Service
public class GreetingService {

    public String greet() {
        return "Hello from a bean";
    }
}

At startup, component scanning finds this class, calls its constructor once, and registers the result under the name greetingService. Your code never calls new GreetingService().

The stereotype annotations

@Component registers a bean. @Service, @Repository and @Controller each register a bean and state its role. Spring treats @Service and @Component identically at runtime; the difference documents intent for the next reader. @Repository differs materially: Spring translates persistence exceptions thrown from classes carrying it.

02Singleton by default

Spring creates one instance per bean definition and shares that instance across the whole application. Two controllers that declare a GreetingService dependency receive the same object.

Consequence

Shared instances make bean state dangerous. Every concurrent request touches the same field on a singleton bean, so mutable instance state introduces a race condition that load testing finds and unit tests do not. Keep beans stateless: pass state through method parameters and return values. Reject mutable fields on beans in review unless the author can name the synchronisation strategy.

03Injection: three forms, one correct

Spring supplies dependencies through constructors, setters, or fields. Use constructors.

Field injection — reject this

Do not write this
@RestController
public class GreetingController {

    @Autowired                      // Do not do this.
    private GreetingService service;

    @GetMapping("/hello")
    public String hello() {
        return service.greet();
    }
}

Constructor injection — use this

src/main/java/com/example/demo/GreetingController.java
@RestController
public class GreetingController {

    private final GreetingService service;

    // Spring passes the dependency here. No annotation required:
    // a single constructor is injected automatically.
    public GreetingController(GreetingService service) {
        this.service = service;
    }

    @GetMapping("/hello")
    public String hello() {
        return service.greet();
    }
}

Since Spring 4.3, a class with exactly one constructor needs no @Autowired annotation. Spring injects that constructor automatically.

Constructor injection wins for four specific reasons:

  • The field becomes final. Nothing reassigns the dependency after construction, which removes a class of bug and makes the object safe to publish across threads.
  • The object cannot exist in an invalid state. A constructed instance has every dependency it needs. Field injection constructs the object first and populates it afterwards, so a window exists where the fields hold null.
  • Tests need no framework. Call the constructor directly:
A unit test with no Spring context
class GreetingControllerTest {

    @Test
    void greets() {
        // No Spring context. Just a constructor call.
        var controller = new GreetingController(new GreetingService());

        assertThat(controller.hello()).isEqualTo("Hello from a bean");
    }
}
  • The constructor exposes design problems. A constructor taking eight dependencies is visibly wrong, and it tells you the class does too much. Field injection hides that signal, because eight annotated fields look no worse than two.
In review

Reject @Autowired on a field. The counter-argument you will hear is that constructors are verbose; the answer is that the verbosity is the diagnostic. Setter injection has one legitimate use — a genuinely optional dependency — and you will encounter that case rarely enough to treat each instance individually.

04When Spring cannot decide

Declare two beans that both satisfy one dependency and startup fails with a message that names the problem and the fixes:

Parameter 0 of constructor in com.example.demo.GreetingController
required a single bean, but 2 were found:
        - englishGreetingService: defined in ...
        - frenchGreetingService: defined in ...

Action:
Consider marking one of the beans as @Primary, updating the consumer
to accept multiple beans, or using @Qualifier to identify the bean
that should be consumed

Three resolutions exist, in descending order of preference:

  • @Qualifier("englishGreetingService") on the constructor parameter. Explicit at the point of use, which is where the next reader looks.
  • @Primary on one bean definition, marking it the default. Use this when one implementation genuinely is the normal choice and the other is an exception.
  • Accept a List<GreetingService> when you actually want every implementation, which is the correct shape for strategies and validators.

05Beans for classes you do not own

Stereotype annotations require editing the class. For a class from a library, declare the bean in a configuration class instead:

src/main/java/com/example/demo/ClockConfiguration.java
@Configuration
public class ClockConfiguration {

    // Use @Bean when you do not own the class and therefore
    // cannot annotate it with @Service or @Component.
    @Bean
    public Clock systemClock() {
        return Clock.systemUTC();
    }
}

Spring calls systemClock() once and registers the returned object as a bean named systemClock. Inject a Clock anywhere and Spring supplies this instance.

This is how auto-configuration works

Spring Boot's auto-configuration consists of @Configuration classes carrying @Bean methods guarded by conditions. The Flyway beans from Lesson 02 arrive exactly this way: a configuration class declares them, and a condition activates it when spring-boot-starter-flyway sits on the classpath. Auto-configuration uses no mechanism you have not now seen.

06Check yourself

What does the ApplicationContext hold?

The ApplicationContext is the registry of beans. Spring builds it at startup, constructs each bean once, and supplies those instances wherever a dependency declares the matching type.

Why does constructor injection beat field injection?

The field becomes final, the object never exists half-constructed, and tests call the constructor without starting Spring. A large constructor also exposes a class doing too much, which field injection conceals.

Two beans satisfy one dependency and no qualifier exists. What happens at startup?

Spring fails fast and names both candidates. Resolve it with @Qualifier at the injection point, @Primary on the default bean, or by accepting a List when you want every implementation.
