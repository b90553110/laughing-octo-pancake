Database migrations with Flyway

Version the schema in your repository. Apply it in order, exactly once, on every environment.

~20 minutes · Spring Boot 4.1.1 · Flyway 12.4.0 · PostgreSQL
Versions, defaults and error strings verified against Maven Central artifacts. I did not execute this code; you will.

A database schema is state. State that lives outside version control diverges between environments, and that divergence surfaces as a production failure no local test reproduces.

Flyway eliminates the divergence with one constraint: the schema is an ordered sequence of SQL files in your repository, and Flyway applies each file exactly once per database. Your repository then describes the schema of every environment authoritatively.

01The model

Flyway creates one table, flyway_schema_history, and derives every decision from it. Flyway inserts one row per applied migration:

rank | version | description        | checksum   | ok
-----+---------+--------------------+------------+---
   1 | 1       | create users table | 1284759302 | t
   2 | 2       | add last login     | -839201847 | t

At startup, Flyway reads that table, compares it against the migration files on the classpath, and takes one of three actions per file:

  • No matching row — Flyway runs the file, then inserts a row.
  • Matching row, identical checksum — Flyway skips the file.
  • Matching row, different checksum — Flyway aborts startup.

The third action enforces the rule in §06. Every Flyway behaviour that surprises people follows from these three lines.

Why not ddl-auto=update

Hibernate's spring.jpa.hibernate.ddl-auto=update also reconciles the schema to your entity classes. Reject it for three specific reasons: it produces no artifact you can review before it runs, it cannot express changes that do not derive from entity classes (data backfills, index type and concurrency, multi-step column renames), and it records nothing about what it changed.

02Add the dependencies

Add four dependencies. Two of them trip people on current versions.

pom.xml — inside <dependencies>
<!-- Spring Boot 4: the STARTER. flyway-core alone does nothing. -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>

<!-- Flyway 10+: your database's support module, added separately -->
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-database-postgresql</artifactId>
</dependency>

<!-- JDBC support and a driver -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>
</dependency>
Trap 1 · Spring Boot 4

Spring Boot 3 auto-configured Flyway from flyway-core. Spring Boot 4 requires spring-boot-starter-flyway. With flyway-core alone, Boot 4 starts the application normally, runs no migrations, and logs no error. Diagnose this failure by its signature: the application starts, and the tables do not exist.

Trap 2 · Flyway 10 and later

Flyway 10 moved database support out of flyway-core into per-database modules. Omit the correct module and Flyway aborts startup with Unsupported Database. The artifact names are inconsistent:

  • PostgreSQL — flyway-database-postgresql
  • Oracle — flyway-database-oracle
  • MySQL and MariaDB — flyway-mysql (no "database" segment)
  • SQL Server — flyway-sqlserver (no "database" segment)

H2 and SQLite require no module, which is why tutorials that demonstrate against H2 never mention this.

Neither Flyway dependency declares a <version>. The parent POM from Lesson 01 manages both. Spring Boot 4.1.1 manages Flyway 12.4.0 and lists every Flyway database module.

Recommendation

Flyway's current standalone release is 13.5.0, ahead of the 12.4.0 that Spring Boot 4.1.1 manages. Do not override the managed version. Spring Boot tests its auto-configuration against the version it manages, and Flyway has relocated classes across major versions before. Upgrade the Spring Boot version deliberately instead of raising one library out of a tested set.

03Write the first migration

Flyway reads migrations from classpath:db/migration by default. Keep that location.

src/main/resources/
└── db/
    └── migration/
        ├── V1__create_users_table.sql
        ├── V2__add_users_last_login.sql
        └── V3__create_orders_table.sql

Flyway parses the filename. Each segment carries meaning:

V2__add_users_last_login.sql
│ │  └── description: underscores render as spaces
│ └──── version: Flyway sorts numerically, not as text
└────── prefix: V marks a versioned migration

Two underscores separate version from description.
src/main/resources/db/migration/V1__create_users_table.sql
-- V1__create_users_table.sql

CREATE TABLE users (
    id           BIGSERIAL PRIMARY KEY,
    email        VARCHAR(255) NOT NULL UNIQUE,
    display_name VARCHAR(100) NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_users_email ON users (email);

Flyway executes this file as plain SQL against your database. It applies no abstraction layer, so you can use any feature your database supports, and you own every portability decision.

04Configure the datasource

src/main/resources/application.properties
spring.datasource.url=jdbc:postgresql://localhost:5432/demo
spring.datasource.username=demo
spring.datasource.password=demo

# Flyway owns the schema. Hibernate verifies it and changes nothing.
spring.jpa.hibernate.ddl-auto=validate

Flyway requires no configuration of its own here. It uses the DataSource that Spring already builds. Only the last line represents a decision.

Recommendation

Set ddl-auto=validate the moment you adopt Flyway. Hibernate then compares the schema against your entities and fails startup on a mismatch, but alters nothing. One component owns the schema and the other verifies it. Two components that both modify the schema produce a database whose shape no one can predict. Reject ddl-auto=update in review on any project that runs migrations.

05Run it

Start the application with ./mvnw spring-boot:run. Flyway runs before the rest of the application context initialises, so your code never observes a partially migrated database:

Flyway Community Edition 12.4.0 by Redgate
Database: jdbc:postgresql://localhost:5432/demo (PostgreSQL 16.2)
Successfully validated 2 migrations (execution time 00:00.031s)
Migrating schema "public" to version "1 - create users table"
Migrating schema "public" to version "2 - add last login"
Successfully applied 2 migrations (execution time 00:00.094s)

Start the application a second time. Flyway validates two migrations and applies none. The same command therefore produces the correct result against an empty database, your local database and production.

Do this

Add a second migration, then restart:

V2__add_users_last_login.sql
-- V2__add_users_last_login.sql

ALTER TABLE users ADD COLUMN last_login_at TIMESTAMPTZ;

Then query the history table directly:

SELECT version, description, success FROM flyway_schema_history;

06The rule

Rule

Never modify a migration that has run on any machine other than your own. To change the schema, add a new migration.

Violate the rule and you trigger the third action from §01. The checksum Flyway recorded no longer matches the file, so Flyway aborts startup:

Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : 1284759302
-> Resolved locally    : 1902847361

Flyway is behaving correctly here. The error states that some database ran SQL that your repository no longer contains, so your repository can no longer describe that database. Two responses exist, and they are not equivalent:

  • Revert the file to the version Flyway applied, then put your change in a new migration. Choose this in almost every case.
  • Run flyway repair, which overwrites the stored checksums with the checksums of your current files. This is correct only when the SQL logic did not change — a corrected comment, reformatted whitespace. Run it after a logic change and it resolves nothing: it records agreement between a database and a repository that still disagree.
In review

When an engineer proposes repair, ask exactly what changed in the file. If the answer requires more than one sentence, reject repair and require a new migration. Small undocumented edits to applied migrations are how a staging database and a production database stop sharing a shape.

07What to check in review

Apply this checklist to every migration:

  • Compatibility with the deployed application version. During a rolling deploy, the old and new application versions run against the same database simultaneously. Dropping a column that the old version still selects breaks it mid-deploy. A rename therefore requires four steps across separate releases: add, backfill, dual-write, drop.
  • Lock duration on large tables. Creating an index can hold a lock long enough to constitute an outage. PostgreSQL offers CREATE INDEX CONCURRENTLY; identify your database's equivalent before you need it.
  • Irreversible operations. DROP COLUMN deletes data and the Community edition provides no undo. Require justification, or defer the drop to a later cleanup migration.
  • Scope. One logical change per migration. Small migrations fail in ways you can diagnose.
  • Version collisions. Two branches that both add V7__ merge cleanly in Git and then fail at startup. Lesson 03 covers this case in full.

08Check yourself

What does Flyway store in flyway_schema_history?

Flyway stores one row per applied migration, including a checksum of the file. That checksum lets Flyway detect a modification to a migration it already applied.

An engineer corrects a typo in V1__create_users_table.sql, which staging already applied. What happens at the next staging startup?

Flyway compares the file against the recorded checksum and aborts. Correct response: revert the file and add V2__. Use repair only when you are certain the SQL logic did not change.

On Spring Boot 4 you declare flyway-core, and no migration runs. No error appears. Why?

Spring Boot 4 auto-configures Flyway from spring-boot-starter-flyway, not from flyway-core. The silence makes this expensive to diagnose: nothing fails, and the tables simply do not exist.
