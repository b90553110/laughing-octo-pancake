Database migrations with Flyway

Your schema becomes something you version, review and deploy — like the rest of your code. Plus the one rule that keeps it that way.

~20 minutes · Spring Boot 4.1.1 · Flyway 12.4.0 · PostgreSQL
Versions and behaviour checked against Maven Central and the current docs. Unlike Lesson 01, the code here was not executed — you are the one running it. Tell me if anything does not match.

Here is the problem, and you have probably already lived a version of it. Your app needs a new column. You add it to your entity class, and it works on your machine, because something helpfully altered your local database. Then it reaches staging, where nobody ran that, and the app either crashes or — worse — quietly does the wrong thing.

The schema is state, and state that is not versioned is state that drifts. Flyway's answer is almost boringly simple: the schema is a sequence of SQL files, in your repository, applied in order, exactly once. That is the whole idea. Everything else is bookkeeping.

01The mental model

Flyway creates one extra table in your database, flyway_schema_history, and it is the entire trick. Every time a migration runs, Flyway writes a row:

rank | version | description        | checksum   | ok
-----+---------+--------------------+------------+---
   1 | 1       | create users table | 1284759302 | t
   2 | 2       | add last login     | -839201847 | t

On every startup, Flyway reads that table and compares it against the migration files on your classpath. Three outcomes:

  • A file it has no row for → run it, then record it.
  • A file matching a row, same checksum → already done, skip it.
  • A file matching a row, different checksum → stop. Refuse to start.

That third case is the one people fight with, and it is also the one doing the real work. Hold onto it; we come back to it in §06.

Why this beats the alternative

Hibernate's ddl-auto=update can also make your schema match your entities. It cannot tell you what it will do before it does it, cannot be reviewed in a pull request, and cannot express anything that is not derivable from entity classes — backfills, index strategy, a two-step column rename. It is a development convenience that has taken down production.

02Add it to the build

Two dependencies, and both of them are places people get stuck on current versions:

pom.xml — inside <dependencies>
<!-- Boot 4: the STARTER, not flyway-core on its own -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>

<!-- Flyway 10+: your database's support module, separately -->
<dependency>
  <groupId>org.flywaydb</groupId>
  <artifactId>flyway-database-postgresql</artifactId>
</dependency>

<!-- And a JDBC driver + JDBC support, as usual -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>postgresql</artifactId>
  <scope>runtime</scope>
</dependency>
Trap 1 · Spring Boot 4

In Boot 3 you added flyway-core and auto-configuration picked it up. In Boot 4 that is no longer enough — you need spring-boot-starter-flyway. The failure mode is nasty: nothing errors, your app starts happily, and no migrations run. If you are following a tutorial written for Boot 3 and your tables never appear, this is why.

Trap 2 · Flyway 10+

Database support was split out of flyway-core into per-database modules. Without the right one you get Unsupported Database: PostgreSQL 16.2 at startup. The module names are not consistent, which catches everyone:

  • PostgreSQL → flyway-database-postgresql
  • Oracle → flyway-database-oracle
  • MySQL → flyway-mysql (no "database")
  • SQL Server → flyway-sqlserver (no "database")

H2 and SQLite need no module, which is why so many tutorials never mention this.

Note that neither dependency carries a <version> — the same inheritance from Lesson 01 is at work. Spring Boot 4.1.1 manages Flyway 12.4.0, and every Flyway module is in its dependency list.

Tech lead note

Flyway's own latest release is 13.5.0, ahead of the 12.4.0 Boot manages. Resist the urge to pin it up. Boot's managed version is the one its auto-configuration was tested against, and Flyway's major versions have moved things before. Upgrade the whole Boot version deliberately; do not cherry-pick one library out of a tested set.

03Write your first migration

Migrations live in src/main/resources/db/migration — that is the default, and there is rarely a good reason to change it.

src/main/resources/
└── db/
    └── migration/
        ├── V1__create_users_table.sql
        ├── V2__add_users_last_login.sql
        └── V3__create_orders_table.sql

The filename is not decoration. Flyway parses it:

V2__add_users_last_login.sql
│ │  └── description: underscores show as spaces
│ └──── version: sorts numerically, not as text
└────── prefix: V = versioned, runs exactly once

Two underscores between version and description.
src/main/resources/db/migration/V1__create_users_table.sql
-- V1__create_users_table.sql

CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,
    email       VARCHAR(255) NOT NULL UNIQUE,
    display_name VARCHAR(100) NOT NULL,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX idx_users_email ON users (email);

It is plain SQL for your database. No abstraction layer, no DSL — which means you can use anything your database can do, and you own the portability question yourself.

04Point it at a database

src/main/resources/application.properties
spring.datasource.url=jdbc:postgresql://localhost:5432/demo
spring.datasource.username=demo
spring.datasource.password=demo

# Let Flyway own the schema; Hibernate must not touch it.
spring.jpa.hibernate.ddl-auto=validate

Flyway needs no configuration of its own here — it uses the DataSource Spring already built. Only that last line is a decision:

Tech lead note

ddl-auto=validate tells Hibernate to check the schema matches your entities and fail loudly if not, rather than altering anything. That is the setting you want the moment Flyway exists: one system owns the schema, and the other verifies it. Two systems both trying to own it is how you get a schema nobody can reason about. If you see ddl-auto=update in a pull request on a project with migrations, block it.

05Run it

Just start the app — ./mvnw spring-boot:run. Migrations run before the rest of the context comes up, so your app never sees a half-migrated database:

Flyway Community Edition 12.4.0 by Redgate
Database: jdbc:postgresql://localhost:5432/demo (PostgreSQL 16.2)
Successfully validated 2 migrations (execution time 00:00.031s)
Migrating schema "public" to version "1 - create users table"
Migrating schema "public" to version "2 - add users last login"
Successfully applied 2 migrations (execution time 00:00.094s)

Start it again and Flyway will report validating 2 migrations and applying none. That is idempotency: the same command is safe to run on an empty database, your laptop's database, and production, and it does the right thing in each case.

Do this

Add a second migration and restart:

V2__add_users_last_login.sql
-- V2__add_users_last_login.sql

ALTER TABLE users ADD COLUMN last_login_at TIMESTAMPTZ;

Then look at the history table directly:

SELECT version, description, success FROM flyway_schema_history;

Seeing your own two rows in there is the moment the model clicks.

06The one rule

Here is the rule the whole tool rests on:

Never

Never edit a migration that has been applied anywhere but your own machine. To change something, write a new migration.

Break it and you get the third case from §01 — the checksum in the database no longer matches the file, and the app refuses to start:

Migration checksum mismatch for migration version 1
-> Applied to database : 1284759302
-> Resolved locally    : 1902847361

Either revert the changes to the migration,
or run repair to update the schema history.

This error is Flyway working correctly. It is telling you that a machine somewhere ran SQL that no longer exists in your repository, so your repository can no longer tell you what that database contains. Two ways out, and they are not equal:

  • Revert the file to what was actually applied, and put your change in a new migration. This is nearly always right.
  • flyway repair rewrites the stored checksums to match your files. Legitimate only when you are certain the SQL logic did not change — a fixed comment, a whitespace tidy. Used on a real change, it does not fix anything; it hides the mismatch and leaves the database and repository silently disagreeing.
Tech lead note

When someone reaches for repair, my question is always the same: what actually changed in that file? If the answer takes more than one sentence, revert and write a new migration. "It's just a small fix" is how a staging database and a production database stop being the same shape.

07What I look for in review

You asked to be taught as a lead, so here is the checklist I actually apply to a migration:

  • Is it backwards compatible with the currently deployed code? During a rolling deploy, old and new application versions run against the same database at once. Dropping a column the old version still selects breaks it mid-deploy. Renames become add → backfill → dual-write → drop, across several releases.
  • Will it lock a large table? Adding an index on a big table can hold a lock long enough to be an outage. PostgreSQL has CREATE INDEX CONCURRENTLY; know your database's equivalent.
  • Is anything irreversible? A DROP COLUMN is a data deletion with no undo in the free edition. Justify it, or postpone it to a later cleanup migration.
  • Is it one logical change? Small migrations fail in ways you can understand.
  • Is the version number going to collide? Two branches both adding V7__ merge cleanly in git and then fight at startup. Some teams use timestamps (V20260910143000__) for exactly this reason.

08Check yourself

What does Flyway keep in flyway_schema_history?

One row per applied migration, with a checksum of the file's contents. That checksum is what lets Flyway detect a migration being changed after the fact.

A teammate fixes a typo in V1__create_users_table.sql, already applied in staging. What happens there?

Validation compares the file against the recorded checksum and refuses to start. Correct fix: revert the file and write V2__. Reach for repair only if you are certain no SQL logic changed.

On Spring Boot 4 you add flyway-core and your migrations never run — no errors. Why?

Boot 4 auto-configures Flyway from spring-boot-starter-flyway, not from flyway-core alone. The silence is what makes it expensive: nothing fails, the tables just are not there.
