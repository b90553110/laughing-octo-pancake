The rule

Rule

Never modify a migration that has run on any machine other than your own. To change the schema, add a new migration.

Practices

PracticeReason
Never modify an applied migrationThe rule the tool rests on. Enforce it in CI, not in review.
One migration per pull requestFewer collisions, and renumbering stays trivial.
Create the migration lateA migration written on day one has two weeks to collide.
Use UTC timestamp versionsOn teams of three or more. Removes duplicate versions entirely.
Squash your branch's migrationsReviewers read the end state, not three intermediate diffs.
Rebuild from empty before reviewCatches migrations that only work against your local state.
Keep seed data in a separate locationSeparate by configuration, never by comment.
Set ddl-auto=validateFlyway owns the schema; Hibernate verifies it.
Deploy migrations before dependent codeA code rollback then needs no schema rollback.
Migrate from the pipeline, not by handManual runs create history rows no repository explains.

Startup sequence

  1. Spring builds the DataSource.
  2. Flyway runs before the rest of the context: it creates flyway_schema_history if absent, validates checksums, then applies pending migrations.
  3. Hibernate validates the schema against your entities (ddl-auto=validate).
  4. The application starts. Your code never observes a partially migrated database.

Zero-downtime schema changes

During a rolling deploy, the old and new application versions run against the same database. Every migration must remain compatible with the code already deployed.

  • Safe alone: adding a nullable column, adding a table, creating an index concurrently.
  • Unsafe alone: dropping or renaming a column, adding a NOT NULL column without a default, narrowing a type.
  • Renaming a column takes four releases: add the new column, backfill it, write both and read the new one, then drop the old one.

Which tool for which problem

  • Rebuild the database — iterating on your own unmerged migration. Use this by default.
  • clean — wipes the schema. Spring Boot disables it. Enable it in a development profile only.
  • repair — fixes checksum rows after a cosmetic edit, or clears a failed-migration row. It re-runs no SQL.
  • baseline — adopts a pre-existing database. Run once.
  • Renumber — resolves duplicate versions and late arrivals. Only on a migration that has not run on a shared environment.

Review checklist

  1. Compatible with the currently deployed application version?
  2. Does it hold a lock on a large table?
  3. Does it delete data or narrow a type irreversibly?
  4. One logical change?
  5. Could the version collide with another branch?
  6. Has it run against production-sized data?
