Naming, properties, modules and the errors you will actually hit.

The rule

Never

Never edit a migration that has been applied anywhere but your own machine. To change something, write a new migration.

File naming

FilenameMeaning
V2__add_last_login.sqlVersioned. Runs once, in version order. The normal case.
R__user_summary_view.sqlRepeatable. Re-runs whenever its checksum changes. Views, functions.
U2__undo_last_login.sqlUndo. Paid editions only — do not plan around it.
V2.1__tweak_index.sqlDots allowed in versions. 2.1 sorts after 2, before 3.
V20260910__add_orders.sqlTimestamp versions. Avoids merge collisions between branches.

Spring Boot properties

PropertyEffect
spring.flyway.enabledDefault true. Set false to disable, e.g. in a test slice.
spring.flyway.locationsDefault classpath:db/migration. Comma-separated; filesystem: also works.
spring.flyway.baseline-on-migrateDefault false. True adopts an existing non-empty database.
spring.flyway.baseline-versionVersion to record for that adopted starting state.
spring.flyway.validate-on-migrateDefault true. Leave it on. This is the safety net.
spring.flyway.out-of-orderAllow a lower version to apply after a higher one. Rarely wise.
spring.flyway.schemasWhich schema(s) to manage.
spring.jpa.hibernate.ddl-auto=validateNot Flyway, but set it. Hibernate checks; Flyway owns.

Errors, decoded

MessageCause and fix
Unsupported Database: XMissing the per-database module. See the table above.
Migrations simply never runOn Boot 4: you have flyway-core but not spring-boot-starter-flyway.
Checksum mismatchAn applied migration was edited. Revert it and add a new one.
Found non-empty schema without historyExisting database. Set baseline-on-migrate=true, once, deliberately.
Detected failed migrationA migration died partway. Fix the SQL, clean the partial state, repair.
Table already existsHibernate ddl-auto created it first. Set ddl-auto=validate.

Startup sequence

  1. Spring builds the DataSource.
  2. Flyway runs, before the rest of the context: creates flyway_schema_history if absent, validates checksums, applies anything pending.
  3. Hibernate validates the schema against your entities (ddl-auto=validate).
  4. The application starts. It never observes a half-migrated database.

Zero-downtime schema changes

During a rolling deploy, the old and new versions of your app run against the same database. Every migration must be compatible with the code already deployed.

  • Safe: adding a nullable column, adding a table, adding an index (concurrently, on large tables).
  • Unsafe alone: dropping or renaming a column, adding a NOT NULL column without a default, narrowing a type.
  • Renaming a column is four releases, not one: add the new column → backfill it → write to both, read the new → drop the old.

Review checklist

  1. Compatible with the currently deployed application version?
  2. Will it hold a lock on a large table?
  3. Anything irreversible — a drop, a truncate, a narrowing type change?
  4. One logical change per migration?
  5. Could the version number collide with another branch?
  6. Has it been run against a copy of production-sized data?
